# Easymesh: 유·무선 단말 연결 이벤트 처리 요약

무선(STA) 연결/이탈은 **드라이버/호스트apd → wappd → (UNIX 소켓) mapd → 1905daemon** 순으로 전달되며, MAP 토폴로지·클라이언트 DB가 갱신됩니다.  
유선 단말은 **스위치/FDB 조회 결과를 1905daemon이 주기적으로 반영**하는 방식이며, 무선과 같은 `WAPP_CLIENT_NOTIFICATION` 경로를 타지 않습니다.

---

## 1. 무선 단말 (Wi‑Fi STA)

### 1.1 wappd: 이벤트 수신과 로컬 테이블

- **진입점**: `wapp_event_handle()`에서 `WAPP_CLI_JOIN_EVENT` / `WAPP_CLI_LEAVE_EVENT` 등으로 분기 (`wappd/common/wapp_cmm.c`).
- **JOIN**: `wdev_cli_join_handle()`  
  - 먼저 `wdev_cli_query_rsp_handle()`을 호출해 AP 쪽 클라이언트 엔트리를 맞춘 뒤, MAP용 메시지를 만듭니다 (`wappd/common/wdev.c`).
- **LEAVE**: `wdev_cli_leave_handle()` / `wdev_cli_all_leave_handle()`에서 이탈 처리 및 MAP 알림.

**wappd 내부에 쌓이는 대표 데이터**

| 위치 | 의미 |
|------|------|
| `struct ap_dev *ap` → `ap->client_table[]` | AP에 연결된 STA 목록 (`struct wapp_sta`) |
| `ap->num_of_assoc_cli` | 연결 STA 수 (연결 시 증가, 이탈 시 감소) |
| `sta->sta_status` | `WAPP_STA_CONNECTED` / `WAPP_STA_DISCONNECTED` |
| `sta->mac_addr`, `sta->bssid`, `sta->assoc_req[]`, `sta->assoc_req_len` | Assoc 요청 프레임 등 (MAP 알림에 실음) |
| `event_data->cli_info` (`wapp_client_info`) | 드라이버/쿼리에서 온 STA 정보 (MLO 필드 포함 시 `MAP_R6`) |

`wdev_cli_query_rsp_handle()`에서 `cli->sta_status == WAPP_STA_CONNECTED`이면 `ap->num_of_assoc_cli++`, `sta->sta_status = WAPP_STA_CONNECTED`, `wapp_fill_client_info()`로 `sta`를 채웁니다.

### 1.2 wappd → mapd/1905: `WAPP_CLIENT_NOTIFICATION`

- `map_send_assoc_cli_msg()` → `map_build_assoc_cli()` (`wappd/map/map.c`)  
  - 패킷 타입: `WAPP_CLIENT_NOTIFICATION`  
  - 페이로드: `struct client_association_event` / 내부 `map_assoc_evt`  
  - **JOIN**: `assoc_evt = STA_JOIN` (코드상 `1 << 7` → **0x80**)  
  - **LEAVE**: `assoc_evt = STA_LEAVE` (0), `reason`에 disassoc 사유  
- 전송: `map_1905_send()` (`wappd/map/map_1905.c`)

### 1.3 mapd: 토폴로지 + 클라이언트 DB

**수신**: `wapp_if.c`에서 `WAPP_CLIENT_NOTIFICATION`을 받으면 `wlanif_handle_client_notification()`을 eloop로 등록합니다.

**처리 순서(요지)**

1. BSSID로 `bss_info` 조회 실패 시 이벤트 폐기.
2. `topo_srv_parse_wapp_client_notification()` (`mapd/src/topologySrv/wappEvent.c`)  
   - `topo_srv_update_assoc_client_info()`로 **자기 1905 디바이스의 무선 클라이언트 리스트** 갱신.  
   - 성공 시 `map_1905_Set_Sta_Notification_Info()`로 **1905daemon에 `LIB_CLIENT_NOTIFICATION`** 전달.
3. JOIN 시 추가로:
   - `mapd_user_wireless_client_join()` (앱/유저 IF 알림, `SUPPORT_MULTI_AP`)
   - `client_mon_handle_local_join()` → **`global->dev.client_db[]`** 에 트래킹/스티어링용 엔트리 갱신 (`mapd/src/clientMon/client_mon.c`)
   - Assoc IE 파싱·capability 갱신 등 (`parse_assoc_req`, `fill_assoc_client_caps` 등, 빌드 옵션에 따라)

**mapd에 쌓이는 대표 데이터**

| 구조 / 변수 | 의미 |
|-------------|------|
| `struct own_1905_device *ctx` → 소유 `struct _1905_map_device *device` | 로컬 MAP 디바이스 뷰 |
| `device->wlan_clients` (`struct connected_clients` SLIST) | 무선 단말(연결 클라이언트) 목록 — BSSID·MAC·`is_APCLI` 등 |
| `device->assoc_clients` (`struct associated_clients` SLIST) | Assoc 기준 클라이언트 — `bss` 포인터, `client_addr`, `last_assoc_time`, `assoc_time` 등 |
| `global->dev.client_db[client_id]` (`struct client`) | 스티어링/모니터링용 클라이언트 DB — `bssid`, `curr_channel`, `is_remote`, capability 플래그 등 |
| `topo_srv_update_assoc_client_info()` 내 분기 | `cinfo->assoc_evt == 0x80` 이면 JOIN, 아니면 LEAVE로 리스트에서 제거 |

`topo_srv_update_assoc_client_info()`는 `mapd/src/topologySrv/topologySrv.c`에 있으며, JOIN 시 `wlan_clients`/`assoc_clients`에 삽입·갱신하고 LEAVE 시 제거합니다.

### 1.4 1905daemon: 1905.1 토폴로지 알림

**수신**: `multi_ap.c`에서 `LIB_CLIENT_NOTIFICATION` 분기.

**동작 요지**

- `ctx->sinfo.sassoc_evt`에 STA/BSSID/이벤트 타입 복사, `ctx->sta_notifier = 1`.
- `multicast_cmdu_tx(..., e_topology_notification, ...)` — 토폴로지 변경을 MAP 네트워크에 통지.
- `update_assoc_sta_info()` — AP capability 쪽 연관 STA 정보 갱신.
- `MAP_R2`: `get_assoc_cli_by_mac` / `create_assoc_cli`, 이탈 시 `client->disassoc` 등.
- 이탈 시 토폴로지 디스커버리 DB와 맞지 않으면 `delete_exist_topology_discovery_database` 등으로 정리.
- **백홀 APCLI**로 붙은 경우(`pevt->is_APCLI` && JOIN): 해당 인터페이스에 대해 `discovery_at_interface_link_up` 예약.

**1905daemon 내부에 쌓이는 대표 데이터**

| 위치 | 의미 |
|------|------|
| `ctx->sinfo.sassoc_evt` | 최근 클라이언트 assoc 이벤트 스냅샷 |
| `ctx->sta_notifier` | STA 알림 발생 플래그 |
| `ctx->ap_cap_entry.assoc_clients_head` 등 | 운용 BSS·연관 STA TLV 생성에 사용되는 연결 정보 |
| `MAP_R2` `struct assoc_client` | MAC/BSSID 기준 assoc 클라이언트 레코드 |

무선 단말은 **wappd가 만든 `LIB_CLIENT_NOTIFICATION` 한 번**으로 mapd 토폴로지와 1905 토폴로지가 같이 움직이도록 연결되어 있습니다.

## 2. 유선 단말 (Ethernet / 스위치 포트)

유선 단말은 **wappd의 STA JOIN/LEAVE 이벤트와 별개**입니다. **1905daemon**이 (1) **물리 포트 링크(UP/DOWN)** 와 (2) **스위치가 학습한 MAC 테이블(FDB/ARL 등, 플랫폼에서는 `eth_ops`로 추상화)** 를 따로 보고, 둘을 합쳐 `ethernet_layer`의 `eth_data[]`에 반영한 뒤, 주기 타이머로 **non‑1905 neighbor** 토폴로지를 맞춥니다.

- **포트 상태** → 주로 `eth_data[i].port_valid` (링크가 살아 있는지). DOWN이면 그 포트의 학습 MAC 리스트를 비움.
- **유선 단말 MAC 목록** → `eth_data[i].clients` (`eth_get_table_entry`로 스위치 테이블 덤프). 링크가 살아 있어도 **테이블 덤프 타이밍**에 따라 갱신됨.

### 2.1 포트 링크(UP/DOWN) — `port_valid` 로 관리

`ethernet_layer.c`의 `eth_layer_port_data_update_and_notify()`가 중심입니다.

1. 입력은 `struct port_status_info` — `port`(포트 번호), `status`(**1 = UP, 0 = DOWN**, `ethernet_layer.h` 주석).
2. 해당 포트의 `struct ethernet_port *pport`를 찾아, 이전 값과 다를 때만 `pport->port_valid = port_status->status` 로 갱신.
3. **DOWN(`status == 0`)** 이면 무조건 `eth_layer_port_clients_clear(pport)` — 그 포트에 매달려 있던 `clients` MAC 엔트리를 전부 제거(케이블 분리 시 FDB와 무관하게 리스트를 비움).
4. 값이 **바뀐 경우에만** 등록해 둔 콜백 호출: DOWN → `notifier.down_handler`, UP → `notifier.up_handler` (`ethernet_port_notifier`, 초기화 시 `eth_layer_port_init`에서 상위 레이어가 연결).

**`port_status_info`가 어디서 오나(빌드·플랫폼에 따라 다름)**

| 경로 | 파일 | 동작 요지 |
|------|------|-----------|
| Netlink | `netlink_event.c` | `SWITCH_PORT_CHANGE` 수신 시 `eth_layer_port_data_update_and_notify(context, status)` |
| 내부 worker 소켓 | `worker_task.c` | `!MCR_WIRELESS_EXTEND` 등에서 PHY 포트를 주기 폴링(`eth_layer_update_eth_port_status` → `eth_get_port_status`), 변화 시 `MII_MGR_PORT_STATUS_CAHNGE` 메시지로 수신부에서 동일 함수 호출 |
| Generic Netlink | `p1905_managerd.c` (`DISABLE_SWITCH_POLLING`) | `genl_netlink_recv`로 포트 상태 수신 후 동일 함수 |
| 부팅 직후 | `update_ethenet_port_status_at_bootup()` | 각 포트 `eth_layer_update_eth_port_status(i)` 후 일괄 `eth_layer_port_data_update_and_notify` |

즉 **포트 상태는 “이벤트/폴링으로 들어온 UP·DOWN”을 `port_valid`에 반영**하고, DOWN이면 **해당 포트 클라이언트 리스트를 즉시 비우는** 방식입니다.

### 2.2 포트에 매달린 MAC 목록 (FDB / 스위치 테이블)

- `eth_layer_port_client_update()`  
  - 기존 `eth_data[i].clients` 클리어  
  - `eth_get_table_entry(_eth_ops, &entry_list)` 로 스위치 테이블 수집  
  - **`pport->port_valid == 1` 인 포트만** 엔트리를 `eth_layer_insert_entry(pport, table_entry)` 로 `pport->clients`에 넣음 (링크 다운 포트는 테이블에 있어도 소프트웨어 리스트에는 안 붙음).

**주기**: `p1905_managerd.c`에서 `!MAP_Cer` 일 때 `SWITCH_TABLE_DUMP_TIME`(기본 **45초**, `p1905_database.h`)마다 `non_1905_neighbor_update` 타이머가 다시 등록되며, 그 안에서 `eth_layer_port_client_update()`가 호출됩니다. 포트 링크 변화와 별도로 **주기적으로 FDB를 다시 읽어** 유선 단말 목록을 맞춥니다.

**저장 구조**

| 변수 / 타입 | 의미 |
|-------------|------|
| `eth_data[MAX_LAN_PORT_NUM]` (`struct ethernet_port`) | LAN 포트별 상태·클라이언트 리스트 헤드 |
| `eth_data[i].clients` | `struct ethernet_client_entry` 리스트 (MAC, `port_index`, age 등) |
| `struct ethernet_client_entry` | 스위치에서 본 유선 단말 1대에 대응 |

### 2.3 토폴로지와의 연결

- `topology.c`의 `non_1905_neighbor_update()` → `eth_layer_port_client_update()` 후, 각 이더넷 인터페이스에 대해 `non_1905_neighbor_update_per_itf()` 호출.
- 포트의 `client_entry->mac`으로 1905 디스커버리/응답 DB를 조회해, **MAP 단말이면 non‑1905 이웃 정리**, **아니면** `non_p1905_neighbor_list`에 `non_p1905_neighbor_info` 삽입·삭제 (`itf_mac_addr`, `port_index`).

즉 유선 단말은 **`eth_data[].clients` + `non_p1905_neighbor_dev[]` 리스트**에 반영되며, 무선처럼 `CLIENT_ASSOCIATION_EVENT` TLV를 wappd가 보내는 경로는 사용하지 않습니다.

## 3. 한눈에 보는 경로

```
[무선 STA]
  Driver/hostapd … → wappd: WAPP_CLI_JOIN/LEAVE
       → ap->client_table / num_of_assoc_cli / wapp_sta
       → WAPP_CLIENT_NOTIFICATION (map_build_assoc_cli)
  → mapd: wlanif_handle_client_notification
       → device->wlan_clients, device->assoc_clients
       → client_db[]
       → LIB_CLIENT_NOTIFICATION → 1905daemon
  → 1905: e_topology_notification, ap_cap / assoc_clients_head 갱신

[유선 STA]
  Switch FDB / port status
       → 1905daemon: eth_layer_port_client_update → eth_data[].clients
       → non_1905_neighbor_update → non_p1905_neighbor_dev
  (wappd/mapd 무선 assoc 이벤트 없음)
```

## 4. Controller vs Agent — 이벤트가 달라지나?

**요약: 위 다이어그램의 “이벤트 종류”와 “로컬 처리 파이프라인”은 역할(Controller / Agent)에 따라 바뀌지 않습니다.** STA가 붙은 장비(보통 Agent 쪽 AP, 또는 Controller가 AP를 올린 경우 Controller)에서 동일하게 `WAPP_CLI_*` → `WAPP_CLIENT_NOTIFICATION` → `wlanif_handle_client_notification` → `LIB_CLIENT_NOTIFICATION` → `e_topology_notification` 흐름이 돕니다. `1905daemon`의 `LIB_CLIENT_NOTIFICATION` 처리(`multi_ap.c`)에도 진입 시점에 `ctx->role == CONTROLLER` 같은 분기로 경로를 나누지 않습니다.

달라지는 것은 **같은 이벤트에 덧붙는 부가 동작**뿐입니다.

| 구분 | Controller / Agent에 따른 차이 |
|------|--------------------------------|
| **무선** | `mapd`에서 예: `DATA_ELEMENT_SUPPORT`일 때 Assoc/Disassoc JSON 파일 생성은 **Controller만** (`wlanif_handle_client_notification`, `topo_srv_update_assoc_client_info` 등). 스티어링·CentStr 등 다른 기능도 역할·옵션에 따라 추가 분기. |
| **무선(원격)** | 다른 MAP 노드에 붙은 STA의 연결/이탈은 **그 노드**에서 위 파이프라인이 돌고, Controller는 주로 **1905 Topology Notification 등 CMDU**로 간접적으로 봅니다(로컬 wappd JOIN 이벤트가 Controller에 직접 오는 것과는 별개). |
| **유선** | `non_1905_neighbor_update_per_itf()`에서 **Controller이면서 해당 포트가 WAN**인 경우 non‑1905 이웃 갱신을 건너뛰는 식의 **역할·포트 조건**이 있습니다(`topology.c`). FDB → `eth_data[].clients` 갱신 자체는 공통입니다. |
| **온보딩/BH** | `WAPP_MAP_BH_READY`, DHCP 제어 등은 `DEVICE_ROLE_AGENT` 등으로 분기하는 코드가 `wappEvent.c` 등에 있으나, 이는 **일반 STA assoc 알림 경로와는 다른 이벤트**에 가깝습니다. |

정리하면, **§3 그림의 “무선/유선 단말 연결” 이벤트 체인은 역할로 바뀌지 않고**, **어떤 박스에서 도느냐**(STA가 실제로 연결된 장비)와 **옵션별 부가 처리**만 역할에 따라 달라집니다.

## 5. 참고: 빌드 매크로

실제 심볼·분기는 `MAP_SUPPORT`, `MAP_R2`, `MAP_R6`, `SUPPORT_MULTI_AP`, `EM_PLUS_SUPPORT` 등에 따라 달라질 수 있습니다. 위 설명은 해당 옵션이 켜진 **전형적인 Easymesh 빌드**를 가정합니다.
